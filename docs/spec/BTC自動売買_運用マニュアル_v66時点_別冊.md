## 1. このシステムについて（1分でわかる説明）

GMOコインのBTC/JPY板情報を見て、自動で指値エントリー・利確/損切りを行う自動売買システムです。
現在、**2つの環境が並行して動いています**。

1. **ネイティブWindows運用（仮想資金）**: Windows 11のPC上で常駐プロセス（`trading_engine.py`）
   として動き続ける、従来からの仮想（シミュレーション）トレード。5万円の仮想資金でロジックを
   検証している
2. **real-test隔離環境（実資金、`docker-compose.real-test.yml`）**: 実資金移行フェーズ2として、
   Docker上の隔離環境で実際のGMO口座に少額の実資金を投入し、本番相当の発注ロジックを検証している。
   専用ダッシュボード（`http://127.0.0.1:8502`）を持ち、1と状態ファイル・ポート・APIキーの
   一部を共有しない完全に別の環境として動く

毎晩AIが前日までの成績を見て設定を微調整し、朝6時にその設定を反映して1日を再開する、
というサイクルはどちらの環境でも共通です。

**今後の見通し**: VPS（Ubuntu）への本番移行を、電気代・室温対策のため前倒しする方針になっています
（`VPS構築手順書.md`参照）。VPS本番稼働後は、real-test環境・仮想資金シミュレーションのいずれも
本番と並行運用しない方針が決まっています（システムをシンプルに保つため）。VPS切り替えが完了する
までは、上記2環境が引き続き並行稼働します。

**2026-07以降追加された機能**: このシステムは、売買ロジック・パラメータを一切公開しない範囲で、
毎日の実績（累積損益・当日損益・決済件数・勝率・最大ドローダウン等）をX（旧Twitter）へ自動投稿し、
Instagram・Threads向けのコンテンツ（動画＋キャプション）をTelegram経由で毎朝配信するようになっています。
X投稿は完全自動、Instagram/Threadsへの実際の投稿は人手で行います（詳細は6章）。**これらのSNS投稿は
ネイティブWindows運用（仮想資金）側のみで動いており、real-test環境からは投稿されません。**

## 2. 1日のタイムライン（ネイティブWindows運用・仮想資金側）

| 時刻 | 何が起きるか | 気にする必要があるか |
|---|---|---|
| 00:00 | ログファイルの日付が切り替わる（エンジンの再起動はしない） | 特になし |
| 03:30 | AIが前日までのログを分析し、設定変更を検討する（`BTC_AI_Nightly_Review`） | 完了後にTelegramで報告が来る（内部Bot） |
| 04:30 | 90日より古いログを月単位でzip圧縮する（`BTC_Log_Archive`） | 通常は何も起きない（対象月がある月のみ動作） |
| 05:55 | 前日分の取引サマリーがTelegramに届く（`BTC_Daily_Report`、内部Bot）。決済件数・勝率・実現損益に加えて、サーキットブレーカー詳細・夜間AI議論件数・ポジション復元イベントの有無・監視ハートビート状況・稼働設定（config_version/profile）を含む | 内容を確認する程度でよい |
| 05:55〜06:30 | GMOコインの**日次**メンテナンス時間。新規エントリー停止のみ。**保有ポジションは強制決済されない**（強制決済されるのは土曜の週次メンテナンスのみ） | 特になし（新規エントリー停止のみシステムが自動対応） |
| 06:00 | エンジンが再起動し、AIが決めた新しい設定を読み込む（`BTC_Engine_Restart`）。ポジションを保有中でも正しく復元される | 特になし |
| 06:10 | Xへ日次レポートを自動投稿（`BTC_Public_Report_Post`）。累積損益・当日損益・決済件数・累積/当日勝率・最大ドローダウン・稼働継続日数・当日エントリー回数・サーキットブレーカー発動有無を投稿 | 通常は何もしなくてよい（投稿失敗時は内部Botへアラート） |
| 06:15 | Instagram/Threads向けのSNS投稿用コンテンツ（キャプションテキスト＋AI考察＋動画）が、SNS専用Telegram Bot（`SnsPostBot`）へ届く | 6章の手順で内容確認・手動投稿を行う |
| 毎時 | 孤立プロセスの監視（多重起動・pid不整合）・異常な取引頻度/損益変化の監視・CSVとDBの整合性チェック | 異常があればTelegramで通知が来る（内部Bot） |
| 5分毎 | エンジンが完全停止していないか（プロセス0件かつ緊急停止指示なし）を検知し、自動復旧を試みる（`BTC_Engine_Process_Check`） | 検知・復旧が発生した場合のみTelegramで通知（内部Bot） |
| 5分毎 | （参考）`BTC_Crash_Loop_Check`はDockerコンテナ監視用のため、現在のネイティブ運用では対象サービスが無く実質何もしていない（VPS/Docker移行後に有効化される） | 特になし |
| 15分毎 | 上記の監視スクリプト自体が生きているかの死活監視 | 異常があればTelegramで通知が来る（内部Bot） |
| 土曜09:00〜11:00 | **週次**メンテナンス時間帯（GMO側）。新規エントリー停止に加え、**保有ポジションは強制決済される**（`maintenance_pre_action: "close"`） | 特になし（システムが自動対応） |
| PC起動時 | 2分後にエンジンが自動起動する | Windows再起動後、放置してよい |

**覚えておくこと**: このシステムの「1日」は暦日（00:00）ではなく、06:00のエンジン再起動が起点です。
日次の損益上限（3.5節）や日次レポートも06:00〜翌06:00で計算されています。

**覚えておくこと**: 日次メンテナンスと週次（土曜）メンテナンスでは、ポジションの扱いが異なります。
日次はポジションを持ち越しますが、週次は強制決済されます。どちらの場合でも、エンジン再起動時の
ポジション復元は正しく行われます。

**real-test環境（実資金）のタイムラインは異なります**: real-test環境はAI夜間レビュー・SNS投稿の
自動タスクを持たず、手動で動作確認・監視を行う運用です。詳細は3.5節を参照してください。

## 3. 起動・日常の確認方法

### 3.1 ダッシュボードを開く（ネイティブWindows運用・仮想資金側）
`run_dashboard.bat` をダブルクリックするだけです。エンジンが止まっていれば自動的に起動してから、
ブラウザでダッシュボードが開きます。

### 3.2 稼働状況をざっと確認する
ダッシュボードで以下が見えます。
- 現在のポジション・**総資産（現金＋ポジション評価）**・**現金残高**・累積損益（総資産と現金残高は別の指標として並列表示。LONG/SHORT保有中はこの2つの値が異なるのが正常です。なお、pending中の未約定指値は総資産計算には含まれません）
- 現在適用中の時間帯プロファイル
- `engine_status`（`RUNNING` / `STOPPING` / `STOPPED`）

コマンドで直接確認したい場合:
```powershell
python -c "import sqlite3; conn=sqlite3.connect('live_state.db'); conn.row_factory=sqlite3.Row; print(dict(conn.execute('SELECT * FROM live_state WHERE id=1').fetchone()))"
```

### 3.3 タスクの登録状況を確認する
```powershell
Get-ScheduledTask | Where-Object { $_.TaskName -like "BTC_*" }
```
登録されているタスク（抜粋）: `BTC_AI_Nightly_Review`・`BTC_Anomaly_Check`・
`BTC_Crash_Loop_Check`・`BTC_CSV_Consistency_Check`・`BTC_Daily_Report`・`BTC_Detect_Orphan_Engines`・
`BTC_Engine_AutoStart_OnBoot`・`BTC_Engine_Restart`・`BTC_Log_Archive`・`BTC_Monitor_Heartbeat_Check`・
`BTC_Orphan_Orders_Check`（孤児注文監視、5分間隔、2026-07-28新設）・
`BTC_Public_Report_Post`（X投稿）・`BTC_SNS_Report_Post`（SNS配信）・`BTC_Engine_Process_Check`（完全停止検知）。
いずれも「ログオンの有無にかかわらず実行」（Password方式）で統一されていることを確認済み。

### 3.4 手動でエンジンを再起動したい場合（ネイティブWindows運用側）
```powershell
schtasks /Run /TN "BTC_Engine_Restart"
```
保有ポジションがあっても、再起動時にポジション情報（サイド・数量・エントリー価格等）が
`live_state.db`から正しく復元されます。ただし、念のためメンテナンス時間帯（05:55-06:30、
土曜09:00-11:00）に合わせて実行する方が引き続き安全です（7章参照）。

### 3.5 real-test環境（実資金隔離テスト）の日常操作（2026-07-30新設）

**ダッシュボード**: `http://127.0.0.1:8502`（ネイティブ運用のダッシュボードとはポート・状態ファイルとも別）。

**手動でエンジンを再起動・確認したい場合**:
```powershell
docker compose -f docker-compose.real-test.yml ps
docker compose -f docker-compose.real-test.yml logs -f engine
```

**緊急停止からの「再開」がダッシュボードのボタンでは行えない点に注意**（既知の仕様）:
Docker/Linuxコンテナ内では、ダッシュボードの「▶ 再開」ボタンおよび「AI議論を再実行」ボタンは
`platform.system() == "Windows"`判定によりPowerShellスクリプトの起動をスキップし、ログとUIに
案内メッセージを表示するだけの動作になっています（Windows専用の起動処理をそのまま動かそうと
して`FileNotFoundError: 'powershell.exe'`になっていたバグは修正済みだが、Docker環境向けの
再起動処理自体は今回新設していないため、依然としてボタンでは完結しない）。

- **エンジンの再開**: `manual_stop.flag`削除後は、以下のコマンドで再開する（Dockerの
  `restart: on-failure`は`manual_stop.flag`起因の停止をexit code 0として扱うため自動再起動されない）
  ```powershell
  docker compose -f docker-compose.real-test.yml start engine
  ```
- **AI夜間レビューの手動起動**: ダッシュボードのボタンでは行えないため、`docker compose run --rm ai_review ...`相当のコマンドで別途実行する（具体的な起動コマンドは`ai_review/run_nightly_review.sh`の内容を確認して実行すること。運用ドキュメントへのコマンド明記は仕様書側で未実施のため、実行時は仕様書4.5.4・6.3節と合わせて確認する）

**ログの永続化（2026-07-30対応済み）**: 以前は`docker compose down`でエンジンログが失われる
問題があったが、`log-real-test/`配下へのファイル出力（`engine_YYYY-MM-DD.log`/`.err.log`）が
実装され、コンテナを削除してもログは残るようになった。それでも、緊急停止からの再開時は
`docker compose down`によるリビルドではなく、上記の`docker compose ... start engine`を
まず試すこと（再起動のたびにコンテナを作り直す必要は基本的にない）。

**手数料の扱いについて**: real-test環境の実際の手数料はこの口座・銘柄では0円で確定している
（GMOの取引履歴で確認済み）。ダッシュボード・日次集計の`fee`列が0円のままでも異常ではない。

## 4. 緊急停止・再開の手順

**普段はこの手順だけ覚えておけば十分です（ネイティブWindows運用・仮想資金側）。
real-test環境（実資金）は3.5節の手順を使ってください。**

### 止めたいとき
ダッシュボードの「⏸ 緊急停止（安全決済）」ボタンを押す。

- 保有中のポジションがあれば自動的に安全に決済してから停止します
- 新規エントリーも即座にブロックされます
- 完了すると`engine_status`が`STOPPED`になります
- 停止中は、PCを再起動しても・ダッシュボードを開いても、勝手にエンジンが起動することはありません

### 再開したいとき
ダッシュボードの「▶ 再開」ボタンを押す（停止中のみ押せる）。

- 数秒でエンジンが起動し、`engine_status`が`RUNNING`に戻ります
- **再開前に、ダッシュボードの「システム緊急制御」欄に表示される「停止理由」を必ず確認してください**。手動停止ボタンによる停止なら`manual`と表示されます。`reconciliation_mismatch`・`daily_loss_limit`・`order_rate_limit`のようなサーキットブレーカーによる自動停止の場合は、原因が解消しているかを確認してから再開してください。停止理由が表示されない場合（導入前の古い停止や、理由ファイルが読み取れない場合）は、5章の「サーキットブレーカー発動通知」の有無や、Telegramに届いた通知の内容も合わせて確認すること

**この操作でエラーになったら**: `runtime/manual_stop.flag`というファイルが正しく
作成・削除されているかを確認してください。手動でこのファイルを作成・削除しても
同じ効果があります（ファイルが存在する＝停止指示、存在しない＝通常運転）。停止理由の表示は
`runtime/manual_stop_reason.json`を参照しているだけの補助情報なので、こちらのファイルが
無くても緊急停止・再開そのものは通常通り動作します。

**未約定の指値（pending）を持ったまま停止した場合**: real-test環境では、緊急停止によって
建玉ではなく未約定のエントリー指値をキャンセルするケースがある。この場合の停止理由・通知内容は
「エントリー注文の取消」であり、建玉決済とは扱いが異なる（7章の孤児注文インシデント参照）。

## 5. Telegramに通知が来たときの対処表

**Telegram Botは2系統に分かれています。**

- **内部管理用Bot**（従来からのBot）: 下表の通知全般、日次レポート等
- **SNS投稿用Bot（`SnsPostBot`）**: Instagram/Threads投稿用コンテンツ（動画＋テキスト）のみ。管理用の情報は一切届かない設計

どちらのBotから届いた通知かで、内容の性質（内部管理用 or SNS投稿素材）が決まるので、
取り違えないようにしてください。

| 通知の見出し | 意味 | 対応 |
|---|---|---|
| `[BTC AI議論] 本日の変更内容をお知らせします` | 毎晩の定例報告。正常時も届く | `outlier_rollout`（段階適用中）・`backtest_gated`（悪化判定でブロック）・`clamped`（上下限に丸め）等があれば内容を確認。異常な設定変更ではないか目を通す程度でよい |
| `[BTC AI議論] エラー` | AI議論が失敗した（API通信エラー等） | 3.5の手順で手動リトライ。頻発するなら8章のトラブルシューティングを確認 |
| `[BTC AI議論] エラー（重要）` | `config.json`書き込み失敗 | すぐに`config.json`が壊れていないか手動確認。復旧が必要な場合がある |
| サーキットブレーカー発動通知（`order_rate_limit`） | 発注頻度の上限（1分あたり5回、デフォルト）を超過して自動停止した | 4章の手順で内容を確認し、原因が解消していれば「▶ 再開」で再開する。imbalance反転→短時間での再エントリー往復が原因になりやすい（対策実施済み、下記参照） |
| サーキットブレーカー発動通知（`reconciliation_mismatch`） | 実口座との不整合が2回連続で検知された | 4章の手順で内容を確認し、原因が解消していれば「▶ 再開」で再開する |
| サーキットブレーカー発動通知（`daily_loss_limit`） | その日（06:00起点）の実現損益が、開始時残高の一定割合（デフォルト10%）を超えて悪化した | 未実現の含み損は対象外、確定損益のみでの発火。原因（相場急変・戦略の不調等）を確認したうえで再開を判断する |
| 異常検知アラート | 取引頻度・損益の急変を検知（1時間毎監視） | 内容を見て、実際に異常な挙動でないか確認。必要なら緊急停止する |
| CSV/DB整合性チェックの通知 | その日の決済件数の集計にズレがある | すぐに危険というわけではないが、原因調査が必要（8章参照） |
| 孤児注文監視アラート（2026-07-28新設、5分毎） | GMO側に有効な発注・建玉が残っているのに内部状態と一致しない（孤児注文）ことを検知した | real-test環境で発生した緊急停止時の未キャンセル注文インシデント（7章）を受けて新設。通知が来たらGMO画面で実際の注文・建玉状況を確認し、必要であれば画面から手動キャンセル・決済する |
| クラッシュループ検知 | Dockerコンテナが繰り返し落ちて停止した | 現在のネイティブ運用では対象サービスが存在せず、このアラート自体が発生することは基本的にない。real-test環境・VPS/Docker移行後は意味を持つ |
| エンジン完全停止の検知・自動復旧 | エンジンプロセスが0件（かつ緊急停止指示なし）を検知し、自動復旧を試みた | 復旧に成功したかを確認。失敗が続く場合はPC自体やタスクスケジューラの状態を確認する |
| 死活監視アラート（heartbeat） | 上記の監視スクリプト自体が動いていない | タスクスケジューラでタスクが正常に実行されているか確認（「対話型のみ」設定になっていないか、3.3節参照） |
| `[ALERT] wrapper exception` | PowerShellラッパー自体の例外（スクリプトの実行環境的な問題） | ログ（`log/*.log`）を確認し、Cursorへの修正依頼を検討 |
| 日次レポート（05:55） | 前日分の決済件数・勝率・実現損益に加え、サーキットブレーカー詳細・AI議論件数・ポジション復元イベント・監視ハートビート状況等（2章参照） | 内容を眺める程度でよい（異常時の通知ではない） |
| X投稿失敗アラート（内部Bot） | 06:10のX自動投稿が失敗した | ログ（`log/public_report_*.log`）を確認。X APIの認証情報・クレジット残高も確認する |
| SNS配信失敗アラート（内部Bot） | 06:15のSNS投稿用コンテンツ配信（動画/テキスト生成やTelegram送信）が失敗した | ログ（`log/sns_report_*.log`）を確認。動画生成のみ失敗した場合はテキストのみが`SnsPostBot`に届いているはず |
| `[CRITICAL]` 強制決済失敗（real-test環境） | real modeの緊急停止時、建玉の成行決済が複数回リトライしても成立しなかった | すぐにGMO画面で実際の建玉状況を確認する。`manual_stop.flag`がある限り60秒間隔で自動リトライが続くため、原因（API障害・残高不足等）を確認しつつ様子を見てよいが、長時間続く場合は手動でGMO画面から決済することも検討する |

## 6. SNS/X投稿の日常運用（2026-07以降新設、ネイティブWindows運用側のみ）

### 6.1 X（旧Twitter）
**完全自動**です。毎日06:10に自動投稿されるため、通常は何もする必要がありません。
投稿内容を確認したい場合はXのプロフィールページを見てください（投稿直後は反映に
数分のキャッシュ遅延が出ることがあります）。

### 6.2 Instagram・Threads
**投稿の判断・実行は人手で行います。** 毎朝06:15、SNS専用Bot（`SnsPostBot`）に、
その日のキャプションテキスト（AI考察付き）と、Instagramリール向け動画（.mp4、無音）が届きます。

手順:
1. `SnsPostBot`とのTelegramチャットを開く
2. 送られてきた動画をスマホのカメラロールに保存する
3. **一緒に届いたキャプションテキストの内容に目を通す**（AI考察が生成されている場合、文章として不自然でないか軽く確認する。フォールバックにより不完全な文は基本的に自動で除外される設計だが、念のため）
4. Instagram: 動画をリールとして読み込み、任意のBGMを付け、コピーしたテキストを貼り付けて投稿
5. Threads: テキストを貼り付け、動画を添付して投稿

**投稿するかどうかは判断してよい**内容です（毎日必ず投稿する必要はありません）。
内容に違和感がある日は投稿を見送っても問題ありません。

### 6.3 注意点
- `SnsPostBot`から届く内容は、投稿してそのままコピペしても安全な内容だけに限定されています（実口座残高やエラーログ等の管理用情報は一切含まれません）
- 逆に、内部管理用Bot（5章）から届く内容は、SNSに貼り付けないでください（サーキットブレーカーの詳細等、非公開情報が含まれます）
- real-test環境（実資金）からはSNS投稿は行われません。将来VPS本番稼働後にSNS投稿機能をどちらの環境から動かすかは、切替時にあらためて確認すること

## 7. やってはいけないこと・注意点

- **`scripts/reset_trading_state.py`を興味本位で実行しない**: `live_state.db`のリセットと
  当日の取引CSVの退避が同時に起きる、本番に実際の副作用がある操作です。動作確認目的でも
  実行すると当日のデータがAI議論の集計対象から一時的に外れます（現在はCSVはコピー方式のため消失はしませんが、それでも不要な実行は避けること）
- **停止中（`manual_stop.flag`が存在する間）は、`ensure_engine_running.ps1`・
  `restart_engine.ps1`のどちらも起動処理をスキップする設計です**。停止したはずなのに
  エンジンが動いている、という場合は`runtime/manual_stop.flag`が正しく作成されているか確認する
- **Cursorに実装を依頼するときは、必ず「依頼した内容以外は追加しない」「絵文字・特殊文字を
  使わない」を伝える**（過去に依頼していない機能の追加や絵文字によるエンコードエラーで
  実際にインシデントが発生しています。詳細は仕様書7章）。**加えて、公開情報（X/SNS投稿）に
  関わる変更を依頼する場合は、「公開してよい項目」を明示的に指定すること**（許可リストの
  境界があいまいなまま依頼すると、意図せず非公開情報や、絶対額と比率の組み合わせのように
  総資産を逆算できてしまう項目が混ざるリスクがある。仕様書4.6.1参照）
- **ログファイル（`market_snapshot_*.csv`等）に新しい列を追加する変更をした日は、
  エンジン再起動前に当日分のログファイルを退避するか、日付が変わるのを待つこと**:
  旧ヘッダのファイルに新ヘッダのプロセスが追記すると列がズレる。バックアップとして
  残す場合も、`log/reset_backup_*/`と同様に`log/`直下から外し、ファイル名も
  `market_snapshot_YYYY-MM-DD.csv`と完全一致させないこと（完全一致させたまま
  別フォルダに置くだけでも通常は自動集計対象外になるが、念のため名前も変えておくと安全）
- **Windows Updateの強制再起動後は、しばらく死活監視アラート（heartbeat stale）が
  まとめて届くことがある**: 再起動でタスクスケジューラの実行が
  一時的に止まっていた期間分の遅延検知なので、直ちに異常というわけではない。
  まずは3.2の方法でエンジン本体（`trading_engine.py`）が生きているか（`engine_status`が
  `RUNNING`か、プロセスIDが実在するか）を優先して確認し、無事であれば
  `Get-ScheduledTask | Where-Object { $_.TaskName -like "BTC_*" } | Get-ScheduledTaskInfo`
  で各タスクの`LastTaskResult`が復旧しているかを見て、しばらく様子を見てよい
- **Task SchedulerにPassword方式でタスクを登録する際、Windowsのログインパスワードを
  ターミナルに貼り付けない**: コマンド実行時に手入力する、または実行後に必ずパスワードを
  変更すること。パスワードがそのままチャットや画面共有ログに残ると露出のリスクがある
- **（2026-07-30追加）real-test環境で緊急停止からの再開時、`docker compose down`→リビルドを
  安易に繰り返さない**: 以前はこの操作のたびにエンジンログが失われていた（現在はログ永続化で
  解消済み、3.5節参照）。まずは`docker compose -f docker-compose.real-test.yml start engine`を
  試すこと。ダッシュボードの「▶ 再開」ボタンはDocker環境では自動再起動を行わない点に注意
  （3.5節参照）
- **（2026-07-30追加）real-test環境と本番用`docker-compose.yml`は、発注用APIキー
  （`GMO_API_KEY_TRADE`）を共有している**: コードレベルの排他ロック（`gmo_trade_key.lock`）は
  同一ホスト・同一`runtime/`ディレクトリ内でのみ有効なため、本番切替時にreal-test環境の
  停止を忘れると二重発注を防げない。VPS本番切替時は必ず`VPS構築手順書.md`7章の手順
  （real-test環境が起動していないことの確認込み）に従うこと

## 8. よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| `live_state.db`が削除できない | ダッシュボード（Streamlit）等がファイルを開いたまま | 関連プロセスを確認・停止してから再試行 |
| `sqlite3.OperationalError: no such table` | プロジェクトルート以外のディレクトリでコマンドを実行している | プロジェクトルートに`cd`してから実行、またはフルパス指定 |
| `schtasks /Create`で「アカウント名とセキュリティIDの間のマッピングは実行されませんでした」 | PowerShellから`%USERDOMAIN%`・`%USERNAME%`を使っている（これらはcmd.exe構文でPowerShellでは展開されない） | PowerShellでは`$env:USERDOMAIN`・`$env:USERNAME`を使う |
| SNS投稿用コンテンツがTelegramに届かない（配信失敗アラートが来る） | `TELEGRAM_SNS_BOT_TOKEN`・`TELEGRAM_SNS_CHAT_ID`が`.env`に未設定 | `.env`に設定後、再実行する（`python scripts\build_sns_report.py --dry-run`で確認可） |
| ダッシュボードの「総資産」と「現金残高」が違う値に見える | LONG/SHORTポジション保有中は正常な差（総資産＝現金＋ポジション評価、現金残高はポジション分を除いた値）。バグではない | 特に対処不要。ポジションを閉じれば両者は一致する |
| Xへの投稿が一時的にプロフィールページから消えたように見える | Xのキャッシュ反映遅延（実際には削除されていない） | 数回ページを再読み込みすれば表示される |
| （real-test環境）「▶ 再開」ボタンを押してもエンジンが起動しない | Docker/Linux環境ではボタンからの自動起動処理を意図的にスキップする設計（8章冒頭の解消済み注記参照） | 3.5節の手順で`docker compose -f docker-compose.real-test.yml start engine`を実行する |
| （real-test環境）発注頻度サーキットブレーカーが短時間に何度も発動する | imbalance反転によるキャンセル後、板に追従してわずかに価格が変わりながら短時間で再エントリーが繰り返され、同一価格判定のクールダウンをすり抜けていた | 2026-07-30にクールダウン判定を同一方向ベース（5秒）に変更し対応済み。効果は経過観察中。再発する場合はログ（`log-real-test/engine_*.log`）の`CANCEL_ORDER`/`[REAL-ORDER]`の間隔を確認する |
| （real-test環境）緊急停止したのに未約定の指値注文がGMO側に残っている（孤児注文） | 2026-07-27〜28に発生したインシデント（7章参照）。現在は修正済みだが、念のため孤児注文監視アラート（5章）が来ていないか確認する | 孤児注文監視アラートが来ていれば内容に従う。来ていなくても不安な場合はGMO画面で有効注文一覧を直接確認する |

その他の詳細なトラブルシューティング・過去のインシデント履歴は仕様書7章を参照してください。

## 10. 困ったときの調べ方

- **まず仕様書を見る**: `BTC自動売買システム_仕様書_66.md`に、このマニュアルより詳しい
  設計判断の経緯・実装の詳細が全て記載されています
- **VPS移行に関する手順**: `VPS構築手順書.md`を参照。VPS本番稼働後は、real-test環境・
  仮想資金シミュレーションのいずれも本番と並行運用しない方針のため、切替時にこのマニュアルも
  合わせて改訂が必要になる見込み
- **ログを見る**: `log/`直下（ネイティブ運用側）・`log-real-test/`直下（real-test環境側）に
  日付ごとのログファイルがあります（取引ログ・板情報スナップショット・
  AI議論ログ・X/SNS投稿ログ・各種監視ログ等）。90日より古いものは`log/archive/`にzip圧縮されて格納されています
- **Cursorに直す依頼をする場合**: このマニュアルや仕様書の項番はCursorには読み込ませていないため、
  依頼文には項番を含めず、変更内容を具体的に書くこと。公開情報（X/SNS投稿）に関わる依頼の場合は、
  7章の注意点も参照すること
