## 3. 戦略ロジックの問題（strategy_logic.py）

コードは Initial commit 以来、実質未変更（ログ永続化のコミットを除く）。8月以降の開発はすべて執行の安全性・監視・SNS投稿側に使われ、シグナル自体は一度も改修されていない。

1. **シグナルが最良気配1枚だけの imbalance**: imbalance = best_bid_size / (best_bid_size + best_ask_size) を1ティックのスナップショットで判定する。実例では best_ask_size = 0.0001 BTC のために imbalance = 0.999 になるようなケースがあり、「壁」は1つの注文が消えれば一瞬で崩れる。depth5（5階層の厚み）・約定データ（trades）・ボラティリティは 2026-07-17 に収集を実装したが、判定には今も使われていない（ログとAIへの集計専用）
2. **継続性・方向の確認がない**: imbalance が閾値（現在0.6764）を一瞬でも超えればエントリー。価格の趨勢（トレンド）、直前の値動き、imbalance の持続時間は見ていない
3. **Maker約定の逆選択**: 指値が約定するのは、相手がその価格を受け入れて価格が指値を通過し始めるとき。つまり「約定した時点でシグナルが古くなっている」ケースに偏る。保有1分未満の勝率32.4%はこの典型的な形
4. **TP/SL が固定 0.15% 同幅**: ボラティリティ連動ではない。値幅の荒い局面ではノイズで SL に触り、静かな局面では TP に届かない。平均勝ち/負けの比（1.18）はこの設定の帰結で、勝率45.9%以上が常時必要になる設計

3. **バックテスト検証ゲートが一度も発動していない**: 93晩で backtest_gated_fields が記録された晩は0件。理由は、(a) TP/SL・閾値の変更自体が Moderator 段階でほぼ却下されゲートまで届かない、(b) ゲート自体が60秒間隔スナップショットによる簡易シミュレーションで、秒単位で動くこの戦略の良し悪しをそもそも判定できない（仕様書 5.4.3 自身が明記している限界。手数料・スリッページも含めていない）

6. **change_outcomes の評価窓が重なりすぎる**: 毎晩変更（理由文だけの晩を含む）があるため、before/after の帰属が曖昧で、「どの変更が効いたか」を学ぶ材料として機能しにくい

## 6. 修正の方向性（優先順・提案であり未着手）

### A. まず止血のルールを決める（設計判断が要る）

### B. 戦略の仮説検証をオフラインでやる（実資金を止めるか最小のまま）
現データでも検証できるもの:
1. 保有時間フィルタ: エントリー後しばらくの SL 判定を volatility 連動に変える（SL = max(0.15%, 5分値幅の k 倍)）、TP/SL 非対称化（例: TP 0.20% / SL 0.15% で必要勝率を下げる）

## 追補（2026-11-06）: 保有時間別集計の解釈の訂正と、決済後値動きの検証

本人の指摘を受けて検証し直した。「保有5分未満に損失が集中」は事実だが、その読み方には注意が要る。

### 指摘のとおりだった点
- 保有時間は「先に SL に当たったものは短く、どちらのバリアにも当たらず生き残ったものは長くなる」という決済ルールの帰結であり、表の形は機械的に生じる。**「長く持てばプラスに転じる」という含みで読むのは誤り**で、元の書き方（「ここが核心」）はその誤読を招くものだった
- 決済理由×保有時間で割ると裏側が見える（2026-08-01〜11-06、ペアリング検証済み5,721件）。1分未満でも TP は256件（+5,717円）あり、SL は541件（-10,958円）。短時間で終わるのは負け筋だけではなく、**短い時間軸では SL 到達が TP 到達より多い**こと自体が表の正体

### 「では持ち続けたらどうなったか」の実測（SL決済 3,262件、60秒スナップショットの mid で追跡）
- 建値まで戻した割合: 30分以内 46.5%／60分以内 58.2%。戻すケースは確かに多い
- しかし固定で持ち続けた場合の損益は、現行より **30分で -8,761円悪化／60分で -15,511円悪化**。決済後のさらなる逆行の中央値は +0.233%（元の SL 幅0.15%を超える）
- SL を2倍（0.30%）に広げ TP は0.15%のまま、というレースで再計算しても、TP先行860件 vs SL先行1,949件で合計 -60,771円（現行 -65,307円）。多少マシになるが黒字転換には程遠く、1敗あたりの損失が約2倍になる分、必要勝率はむしろ上がる
- 結論: 短時間損切りの本質は「早く切りすぎ」ではなく「エントリー直後に逆行する建玉の多さ（勝率そのもの）」。対策の優先度は保有時間の操作ではなく、エントリー条件側（imbalance の継続性・depth5・逆選択の緩和）にある、という当初の提案 B の方向を補強する結果になった

注: スナップショットは60秒間隔の mid 価格。分内のバリア接触は見えず、手数料・スプレッドも含まないため、レース再計算は実績より甘めに出る前提で読むこと。それでも結論は変わらなかった。

## 追補2（2026-11-06）: 手数料の扱いの確定と、口座残高との突合で見つかった差異

外部レビュー（Claude）からの「実績の数字は手数料込みか」という確認に答えるため、コードと口座データを突合した。

### 取引手数料は「未計上」ではなく「ゼロ」が正しい
- このシステムは GMO 取引所レバレッジ（openPositions／closeOrder）。GMO 公式では BTC/JPY の注文手数料は Maker／Taker とも無料
- コードの理論料率も MAKER_FEE_RATE = TAKER_FEE_RATE = 0.0（virtual_trader.py:58-59）。約定イベントに実手数料が含まれればそれを使う作りだが、全期間のエントリー／決済ログ 11,513 件すべて fee = 0
- 損益は実約定価格ベース（gross = 約定価格差 × 数量、net = gross − fee）。スプレッドとスリッページは約定価格そのものに含まれる。よって損益分岐勝率 45.9% は取引損益としてはこの前提で正しい
- 仮に現物式の Taker 0.05% が SL 決済に課金されていたら差額は約2万円規模になるはずで、後述の突合差異（約3,400円）とも整合しない。「課金されていない」ことの傍証になる

### レバレッジ手数料（取引損益の外で引かれる分）
- 朝6:00をまたいだ建玉に評価額 × 0.04%／日（GMO 公式）。全期間で6:00またぎは70件、推定合計 **約336円**。日次集計の実現損益には含まれない

### 突合で見つかった差異（新しい問題）
- 口座の実資産（GMO actualProfitLoss の EOD）は 2026-08-02 の 55,148円 → 2026-11-05 の 43,887円で **-11,261円**。内部の実現損益合計は -7,892円で、**約3,369円の説明できない差**がある（内部残高は決済のたびに実 equity へ同期されるため、残高側は実態に一致する）
- 内訳の見当: レバレッジ手数料 約336円／2026-08-21（PAUSED事故の期間）だけで -473円の差。残り約2,500円は未特定で、エンジン停止・再起動・WS欠落の間に約定した決済が日次集計に載らなかった分が本命候補（ロスカット手数料 0.5%／件≒60円が発生していればその分も含む）
- 結論の修正: 「実績 -7,866円・1日約-81円」は**取引損益としては正しいが、口座ベースの実損失は約-11,300円（1日約-119円）**と見るのが正確。PF も口座ベースではさらに悪い。完全な特定には GMO 側の約定・入出金履歴との全件突合が要る
- あわせて文言の訂正: 結論部の「パラメータの微調整で直る範囲を超えている」は現時点では仮説の強さであり、オフライン検証（提案B）未実施の間は「現行パラメータ空間のままでは分岐を超えられていない」が正確な表現

## 追補3（2026-11-06）: 差異3,369円の突合結果（原因特定）

### 突合の方法と制約
- GMO API（参照専用キー）の /v1/latestExecutions は **約395件・約32時間分しか遡れない**（2026-11-05 09:22 〜 11-06 12:59 JST を取得）。全期間の GMO 側履歴は API では取得不可。この窓で内部 CSV と全件突合し、1件あたりのずれの性質を特定して全期間へ外挿した
