# BTC自動売買 運用モデル（確定）— 2026-11-06

2026-11-06 の会話で本人が確定した運用モデル。開発体制の変更（Cursor製造の終了、じじによる実装一貫体制）と、止血ルールの方針を含む。

## 止血と続行の方針（本人決定）

- 現在残高を起点に仕切り直し、最小サイズで続行しながら検証する（即時停止はしない）
- 止血ルールは口座 equity 基準：起点はルール有効化時点の実残高、起点から −5,000円で停止
- 再開は手動。再開時に起点を自動で付け替えない（付け替えは別の明示操作として記録する）

## 実装セット（詳細設計書どおりの順番）

1. 集計修正：FORCE_CLOSE_REAL の件数系集計漏れ（日次レポート／AIサマリ／change_outcomes／整合性チェッカー）
2. tick記録：板・歩み値の記録開始（戦略には触らない。2週間分が貯まったらエントリー条件のオフライン検証に使用）
3. PnLの切り捨て揃え：決済ごとに GMO と同じ整数円切り捨てで累積。過去分は書き換えず、切替時刻を log/pnl_cutover.json に記録
4. equityガード：決済後同期＋5分ごとの定期確認の2系統で判定。API取得不可時は発動しない。発動時は強制決済せず新規エントリーのみ停止し、手動再開まで再開しない

## 開発・運用の経路

- 正本は GitHub（festallypicco/gmo-btc-ws）。変更はすべてブランチ＋PR。VPS の /opt/gmo-btc-ws は展開先であり、直編集しない（緊急時を除き、その場合も直後に GitHub へ戻す）
- 実装・単体テスト・反映作業はじじが担う。単体テストは作業コピーで実行し、結果を PR に添える
- 反映は本人の承認後すぐ（土曜枠には固定しない）。エンジン再起動が伴うものは建玉のないタイミングで実施し、前後を報告する
- 役割分担：本人＝方針・数字の決定、PRマージ、反映・再開の承認。じじ＝調査・設計・実装・テスト・反映作業・監視・報告・仕様書メンテナンス
- 異常の一次診断（読み取りのみ）は声かけなしで実施し、結果を報告する。エンジンの緊急停止は、実装済みルールによる自動停止と本人の指示のときだけ

## レビューの二重化（2つの目の代替構造）

従来の「Cursor＋Claude の2つのAIで見る」体制の代替として、以下を必須とする。

- 本番に影響する変更は、実装したじじとは別の新規インスタンスに、設計書・PR差分・テスト結果だけを渡して敵対的レビューさせる
- レビュー指摘は、解消するか、本人が明示的に受け入れるまでマージしない
- テストと口座データ突合などの機械的検証を併用する（今回の PnL 切り捨ての件は突合から発見された）
- 最終ゲートは本人の PR レビューとマージ承認

## 文書の正本化

- 本リポジトリの docs/ を文書の正本とする（spec／design／review／operations）
- コード変更の PR には、対応する文書の更新を同じ PR に含める。仕様が変わる変更では仕様書の版もその PR で上げる
- 設計書は実装前に書き、実装が設計からずれた場合は設計書側も直してからマージする
- 最初の保守タスク：2026年10月の SL 未設定監視（本番実装済み・仕様未反映）を仕様書へ取り込み v91 化する

## 数字の土台（突合で確定済み）
