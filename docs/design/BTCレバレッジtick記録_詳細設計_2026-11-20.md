# BTC レバレッジ市場 tick 記録 詳細設計（2026-11-20）

## 1. 背景と目的

2026-11-20 のバックテスト検証（`files/BTCバックテスト検証_2026-11-20.md` 第6章）で、
エンジンはシグナル判定に現物（symbol=BTC）の板を使い、発注・SL はレバレッジ市場
（symbol=BTC_JPY）で執行する二市場構成であることが判明した。tick 記録が現物のみの
ため、約定と SL 執行が起きるレバレッジ市場の再現ができず、候補検証に進めなかった。

本変更は、レバレッジ市場の板（orderbooks）と約定（trades）を現物と同じ形式で
記録し、数週間の蓄積後に再検証できる状態を作る。記録のみの変更であり、
戦略・発注ロジックには一切触れない。

## 2. 設計

### 2.1 購読経路

- 既存の public WebSocket 接続（`WebSocketManager`）へ購読を追加する。別接続は作らない。
- `_on_open` で、レバレッジレコーダーが渡されている場合に限り、現行の
  orderbooks（BTC）/ trades（BTC）に続けて orderbooks（BTC_JPY）/ trades（BTC_JPY）
  を購読する。連続 subscribe の ERR-5003 回避のため、各送信の間に既存と同じく
  2 秒空ける。レコーダーがない場合は従来と完全に同じ通信になる。

### 2.2 ルーティング

- `_on_message` の JSON パース直後、`symbol == "BTC_JPY"` のメッセージは
  記録専用の `_on_leverage_message` へ渡して終了する。現物（BTC）と symbol の
  ないメッセージは従来経路と同一に処理する。
- `_on_leverage_message` は記録だけを行い、次には一切触れない。
  - 現物スナップショット（`_snapshot` / `_depth_stats`）
  - 売買コールバック（`VirtualTrader.on_orderbook_update`）
  - 現物約定バッファ（`_trade_buffer`、market_snapshot 用）
  - メンテナンス検知フラグ
- 板は現物と同じ `_compute_depth_stats`（5階層合計と depth_imbalance）で集計し、
  約定は現物 trades と同じパース規則（side が BUY/SELL、size > 0）で検証する。
- 全体を try/except で包み fail-silent とする。記録経路の例外が取引ループへ
  伝播する経路は構造的に存在しない。

### 2.3 TickRecorder の市場パラメータ化

- `TickRecorder` に `file_prefix` 引数を追加する。既定（""）は従来どおり
  `book_` / `trades_`、`"_lev"` で `book_lev_` / `trades_lev_` になる。
  ロジックは複製せず、ファイル接頭辞だけをインスタンス属性に持つ。
- ファイル名から取引日ラベルを取り出す処理はインスタンス単位とし、自分の
  接頭辞に一致し、かつ日付として解釈できるファイルだけを gzip / 保持削除の
  対象にする。同じ `log/tick/` を共有しても市場間で干渉しない。
- 日界（06:00）・gzip ローテーション・35 日保持・bounded queue（100,000）・
  flush 条件・ディスクガード（空き 5GB 未満で自動停止）は既存仕様を共用する。
  ディスク不足で停止した場合、アラート文面に接頭辞を含め、どちらの市場の
  記録が止まったか分かるようにする（現物側の文面は従来どおり）。

### 2.4 記録形式（現物と同一列）

- `log/tick/book_lev_YYYY-MM-DD.csv`:
  `timestamp_ms,best_bid_price,best_bid_size,best_ask_price,best_ask_size,bid_depth5_size,ask_depth5_size,depth_imbalance`
- `log/tick/trades_lev_YYYY-MM-DD.csv`:
  `timestamp_ms,side,price,size,exchange_timestamp`

### 2.5 エンジン配線

- `trading_engine.py` は起動時にレバレッジ用 `TickRecorder(file_prefix="_lev")`
  を生成し、`_build_ws_managers` 経由で `WebSocketManager` へ渡す。
  start/stop は現物レコーダーと並べて呼ぶ（起動時・PAUSED 再開時・終了時）。

## 3. テスト

- 変更前ベースライン: 404 passed / 10 failed（失敗は既存分のみ:
  test_sns_reel_video 9 件、test_build_public_report 1 件）。
- 追加テスト（tests/test_tick_recorder.py）:
  - `book_lev_` / `trades_lev_` への記録と現物ファイル名で作られないこと
  - 市場間の相互隔離（gzip / 保持削除が相手のファイルに及ばないこと、
    book / trades 両方、同時起動時を含む）
  - BTC_JPY の板・約定がレバレッジレコーダーだけに届き、現物スナップショット・
    売買コールバック・現物約定バッファに混入しないこと
  - レバレッジレコーダーがある場合のみ BTC_JPY 購読が送られること、および
    購読間の 2 秒間隔（ERR-5003 回避の前提）が保たれること
  - レバレッジ記録が例外を投げても現物処理が止まらないこと（fail-silent）
  - `_build_ws_managers` 経由でレバレッジレコーダーが受け渡されること
- 変更後: 411 passed / 10 failed（失敗セットはベースラインと同一）。

## 4. 運用メモ

- 反映後に確認すること: `log/tick/` に `book_lev_*.csv` / `trades_lev_*.csv` が
  書かれていること、現物の book / trades も継続していること、エラーログが
  空であること、equity ガードの起点（43,719円）と armed 状態が維持されていること。
- 購読が 4 本になったため、接続・再接続時の `_on_open` 内の待機は合計
  約 6 秒になる（従来は約 2 秒）。受信開始がその分遅れるが、再接続の
  バックオフ（3〜60 秒）の範囲内であり、実害はない想定。
- ファイル名から日付として解釈できないファイルは gzip / 保持削除の対象外に
  なった（従来は接頭辞が合えば対象だった）。正規の tick ファイルは全て
  `YYYY-MM-DD` 形式のため実害はない。市場間の隔離に必要な変更である。
- 記録量は現物の概ね同程度が追加される見込み。35 日保持と 5GB のディスク
  ガードが上限を抑える。ディスク不足時は市場ごとに記録が止まり、その市場の
  分だけアラートが送られる。
- 本変更は仕様書（v92）への全面反映の対象外とし、変更メモとして本書を残す。
  仕様書へは二市場構成の明記と合わせて別途反映する。
