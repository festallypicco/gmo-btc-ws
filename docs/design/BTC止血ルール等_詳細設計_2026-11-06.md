## 0. 決定事項（本人決定済み）

| 項目 | 決定 |
|---|---|
| 全体方針 | 現在残高を起点に仕切り直し、最小サイズ（0.001 BTC）のまま続行しながら検証する |
| 止血ルール | 口座 equity（GMO actualProfitLoss の実測値）基準。起点 = ルール有効化時点の残高。**起点から -5,000円で新規建玉を停止** |
| 再開 | 手動のみ（自動再開しない。再開時に起点は自動でリセットしない） |
| PnL 記録 | 切替日以降、決済 PnL を整数円へ切り捨て（floor）てから累積する。過去分は書き換えない |
| 実装セット | (1) equity ガード (2) PnL 切り捨て揃え (3) FORCE_CLOSE_REAL の集計漏れ修正 (4) tick 板データ記録 |

現状の参考値: 開始 55,148円（2026-08-02）→ 43,887円（2026-11-05 EOD）= -11,261円。口座ベースの損失ペースは約 -119円/日（取引損益 約-85円 + 切り捨て 約-30円 + レバレッジ手数料 約-4円）。-5,000円は現ペースで約42日分。

## 1. equity ガード（止血ルール）

### 1.1 状態の保存
- 新規ファイル `runtime/equity_guard.json`（live_state.db のスキーマは変更しない）。原子的書き換え（tmp + rename）で保存し、再起動・デプロイをまたいで保持する
- 内容: `baseline_equity`、`baseline_captured_at`、`baseline_position_open`（起点取得時に建玉があったか）、`stop_equity`（= baseline - 5000）、`state`（armed / stopped）、`stopped_at`、`last_equity`、`last_checked_at`、`history`（armed / stopped / cleared / rebaselined のイベントを時刻と equity つきで追記する監査ログ）

### 1.2 起点の取得
- 有効化デプロイ直後に `fetch_real_account_state()`（既存関数。GMO /v1/account/margin の actualProfitLoss）で1回だけ取得して起点とする
- 建玉保有中に取得した場合、actualProfitLoss にはその建玉の評価損益（±25円程度）が混ざるが、5,000円の閾値に対して無視できるため、フラットになるまで待たない。取得時に建玉があった事実だけ history に残す

### 1.3 判定
- 判定タイミングは2系統:
  1. **決済後の equity 同期時**（既存の `_sync_jpy_balance_from_equity_unlocked` の直後）。追加の API 呼び出しなしで、1日約60回の判定機会がある
  2. **5分ごとの定期確認**（`fetch_real_account_state()`）。建玉が開いたまま固まった場合（SL 欠落のような事態）でも、評価損益込みの equity で悪化を捕捉できるようにする
- 判定式: `equity <= stop_equity` で発動。equity は評価損益込みの実測値を使う（内部 PnL は使わない。今回の突合で得た教訓どおり、未知の漏れも equity なら捕捉できる）
- API 取得失敗時は**停止判定をしない**（ネットワーク瞬断で誤停止させない）。失敗が連続する場合は既存の異常検知側に任せ、ガードは「データなしでは発動しない」を原則とする

### 1.4 発動時の動作
- 新規エントリーを即時禁止する。実装は、既存の日次損失チェック（`check_daily_loss_limit`）と同じ入口でガード状態を見る形にし、新しい停止経路を作らない
- **保有中の建玉は強制決済しない**。既存の TP/SL 注文をそのまま生かして決済させ、決済後は再エントリーしない（損失は SL 幅の ±25円程度に bounded。強制決済は板スナップショット近似などの誤差経路を増やすため採らない）。SL が欠落している場合は既存のウォッチドッグが強制決済する
- 既存の `_emit_critical_alert` で通知する（基準値・現在 equity・停止値を明記）。日次レポート（build_daily_report）にもガード状態を表示する
- 日次損失上限（開始残高の10%）とは独立に働く。どちらか先に当たった方が効く。ガードは 06:00 の日次リセットで解除されない

### 1.5 再開と起点の扱い
- 再開は人間の明示操作のみ。`state` を armed に戻す操作を専用に用意し、history に記録する
- 再開しても**起点は自動で動かさない**。起点を現在残高へ付け替える（rebaseline）場合は、それ自体を別の明示操作として history に残す
- 運用注記: 本人が入出金をすると equity が跳ぶ。その場合は起点の付け替えが前提になる（現状、入出金の運用はない）
